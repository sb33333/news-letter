# 프로젝트 목표 및 범위 정의서
(Project Goals and Scope)

## 1. 프로젝트 목표

### 1.1 서비스 목표 (Service Goals)

DevLetter의 서비스 목표는 개발자 및 IT 종사자가 자신의 관심 분야에 해당하는 IT 뉴스와 기술 정보를 효율적으로 확인할 수 있는 환경을 제공하는 것이다.

세부 목표는 다음과 같다.

1. 다양한 외부 사이트의 IT 뉴스 정보를 통합하여 제공한다.
2. 사용자가 관심 있는 기술 분야를 직접 선택할 수 있도록 한다.
3. 관심 분야에 해당하는 뉴스를 선별하여 제공한다.
4. 이메일 뉴스레터를 통해 정기적으로 정보를 전달한다.
5. 향후 사용자 간 기술 정보 공유 및 토론이 가능한 환경을 제공한다.

### 1.2 기술적 목표 (Technical Goals)

| 영역 | 목표 |
|---|---|
| Backend | Java 및 Spring Boot 기반 백엔드 애플리케이션 개발 |
| API | REST API 설계 및 구현 |
| Authentication | Spring Security 기반 인증 구현 |
| Authorization | 사용자 역할 및 권한에 따른 접근 제어 |
| ORM | JPA 기반 데이터 영속성 관리 |
| External Integration | RSS 데이터 수집 및 이메일 서비스 연동 |
| Scheduling | 정기적인 RSS 수집 및 뉴스레터 발송 |
| Testing | JUnit 및 Mockito 기반 테스트 자동화 |
| Container | Docker 기반 애플리케이션 실행 환경 구성 |
| CI/CD | GitHub Actions 기반 빌드, 테스트 및 배포 자동화 |
| Architecture | 모듈러 모놀리스 기반 도메인 설계 및 MSA 전환 가능성 검토 |
| Operations | 로그 관리 및 서비스 운영 환경 구성 |

※ 세부 기술 버전과 라이브러리는 기술 검토 및 설계 단계에서 확정한다.

### 1.3 학습 목표

- 실무적인 백엔드 애플리케이션 아키텍처 설계 경험
- 외부 시스템과의 연동 및 데이터 수집 처리 경험
- 인증(Authentication)과 인가(Authorization)의 차이 및 구현 경험
- 데이터베이스 모델링 및 성능을 고려한 SQL 작성 경험
- 테스트 코드 작성 및 자동화 경험
- CI/CD 파이프라인 구축 및 배포 경험
- 애플리케이션 운영 및 장애 대응 경험

## 3. MVP 개발 범위

MVP(Minimum Viable Product)는 서비스의 핵심 가치를 검증하기 위해 우선적으로 구현할 최소 기능 제품을 의미한다.

초기 버전에서는 뉴스 수집부터 사용자별 뉴스 제공 및 이메일 발송까지의 핵심 흐름을 완성하는 데 집중한다.

### 3.1 MVP 포함 기능 (In Scope)

| 구분 | 기능 | 주요 내용 |
|---|---|---|
| 회원 | 회원가입 및 로그인 | 사용자 인증 |
| 회원 | 관심 분야 설정 | 사용자별 관심 기술 분야 관리 |
| 뉴스 수집 | RSS 출처 관리 | 관리자의 RSS 출처 등록 및 관리 |
| 뉴스 수집 | RSS 자동 수집 | RSS 데이터 주기적 수집 |
| 뉴스 관리 | 중복 데이터 방지 | 동일 뉴스의 중복 저장 방지 |
| 뉴스 관리 | 뉴스 분류 | 카테고리 기반 뉴스 분류 |
| 뉴스 조회 | 뉴스 목록 및 상세 조회 | 공개 뉴스 정보 제공 |
| 개인화 | 관심 분야별 뉴스 조회 | 사용자 관심 분야 기반 뉴스 제공 |
| 뉴스레터 | 구독 설정 | 뉴스레터 구독 및 수신 거부 |
| 뉴스레터 | 이메일 발송 | 관심 분야 기반 뉴스레터 정기 발송 |
| 관리자 | 뉴스 및 수집 상태 관리 | 뉴스 데이터와 RSS 수집 결과 관리 |

### 3.2 MVP 제외 기능 (Out of Scope)

초기 개발 범위에는 포함하지 않으며, 핵심 기능 완성 이후 확장 여부를 검토한다.

| 기능 | 제외 사유 |
|---|---|
| AI 기반 뉴스 자동 분류 | 초기에는 규칙 및 관리자 기반 분류로 충분 |
| AI 뉴스 요약 | 핵심 서비스 흐름 구현 이후 검토 |
| 개인화 AI 추천 | 초기 개인화는 사용자 관심 분야를 기준으로 구현 |
| 댓글 및 토론 기능 | MVP 핵심 가치와 직접적인 관련성이 낮음 |
| MSA 아키텍처 적용 | 초기에는 모듈러 모놀리스 구조로 개발 |
| 실시간 알림 | 초기 서비스 범위에서 제외 |
| 모바일 앱 | 웹 서비스 우선 개발 |

## 5. 프로젝트 성공 기준 (Success Criteria)

프로젝트의 성공 여부를 판단하기 위한 기준을 정의한다.

### 5.1 기능적 성공 기준

1. 관리자가 RSS 출처를 등록하고 관리할 수 있다.
2. 등록된 RSS 출처의 뉴스가 주기적으로 수집된다.
3. 동일 뉴스가 중복 저장되지 않는다.
4. 수집된 뉴스가 기술 분야별로 분류된다.
5. 사용자가 관심 분야를 설정하고 수정할 수 있다.
6. 사용자가 관심 분야에 해당하는 뉴스를 조회할 수 있다.
7. 구독 사용자가 정기적으로 이메일 뉴스레터를 수신할 수 있다.
8. 뉴스레터 수신 거부 설정이 정상적으로 반영된다.

### 5.2 기술적 성공 기준

1. REST API가 정의된 명세에 따라 정상적으로 동작한다.
2. 인증 및 인가 정책이 적용된다.
3. 주요 비즈니스 로직에 대한 테스트 코드가 작성된다.
4. 데이터베이스 제약조건 및 인덱스가 적절하게 설계된다.
5. 외부 RSS 서버 오류가 전체 수집 작업에 영향을 주지 않도록 처리한다.
6. Docker를 이용하여 애플리케이션 실행 환경을 구성한다.
7. CI/CD를 통해 빌드, 테스트 및 배포 과정을 자동화한다.
8. 로그를 통해 주요 작업 및 오류 발생 내역을 확인할 수 있다.

### 5.3 포트폴리오 성공 기준

- 프로젝트의 전체 아키텍처와 데이터 흐름을 설명할 수 있다.
- 주요 기술 선택의 근거를 설명할 수 있다.
- 개발 과정에서 발생한 기술적 문제와 해결 과정을 설명할 수 있다.
- 테스트 및 배포 과정을 시연할 수 있다.
- 모놀리스와 MSA의 구조적 차이 및 전환 필요성을 설명할 수 있다.

※ 구체적인 성능 목표, 테스트 커버리지, 가용성 등의 수치 기준은 요구사항 분석 및 설계 단계에서 결정한다.

## 6. 프로젝트 진행 원칙

1. 핵심 기능을 우선 구현하고 이후 확장 기능을 추가한다.
2. 최신 기술을 무조건 도입하기보다 도입 목적과 필요성을 우선 검토한다.
3. 도메인 간 결합도를 낮추고 유지보수하기 쉬운 구조를 지향한다.
4. 주요 기능은 테스트 코드로 검증한다.
5. 기술적 의사결정과 문제 해결 과정을 문서화한다.
6. 실제 서비스 운영을 고려하여 예외 처리, 로깅, 보안 및 배포 환경을 구성한다.

## 7. 범위 변경 관리

개발 과정에서 새로운 기능이나 기술적 요구사항이 발생할 경우 다음 기준으로 반영 여부를 결정한다.

- 핵심 서비스 가치에 직접적으로 필요한 기능인가?
- MVP 개발 범위에 포함할 필요가 있는가?
- 개발 일정 및 구현 복잡도에 미치는 영향은 무엇인가?
- 향후 확장 기능으로 분리하는 것이 적절한가?

범위 변경 시 기존 개발 일정과 우선순위를 함께 검토한다.
